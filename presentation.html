Research question

Given two years of US flight history and matching weather, can we build a simple, fully explainable delay predictor for the third year — using only SQL?

Architecture — ELT, four layers

Python fetches and loads. PostgreSQL does everything else.

                                  staging.weather_raw      │

                                          │

                                          │

Why ELT not ETL? The database has the heavy machinery — indexes, FKs, set-based ops. Transforms in SQL are version-controlled, replayable, and debuggable in DataGrip.

Capstone

Enrichment — joining weather to flights

Two JOINs against weather_hourly + derived features. ~56s on 1.4M rows.

The two joins

FROM flights f
LEFT JOIN weather_hourly w_dep
  ON w_dep.airport_code = f.origin_airport_code
 AND w_dep.obs_timestamp =
     DATE_TRUNC('hour', f.scheduled_departure)
LEFT JOIN weather_hourly w_arr
  ON w_arr.airport_code = f.dest_airport_code
 AND w_arr.obs_timestamp =
     DATE_TRUNC('hour', f.scheduled_arrival)

LEFT JOIN so flights without a weather match still land in flights_enriched with NULL weather columns.

Capstone

The model is a table

No Python ML. No opaque artefacts. One SQL row per prediction rule.

model_route_hour_weather — rich aggregates per bucket

CREATE TABLE model_route_hour_weather (
    origin, dest, hour_of_day, weather_bucket,                -- the bucket keys

    avg_delay, median_delay, delay_p90,                       -- magnitude (continuous)
    pct_late, pct_cancelled,                                  -- likelihood
    pct_short, pct_average, pct_long, pct_extreme,            -- magnitude distribution
    sample_size,
    PRIMARY KEY (origin, dest, hour_of_day, weather_bucket)
);

The two output dimensions

  • Late-likelihood: low <20%, avg 20-50%, high ≥50%
  • Magnitude: short ≤30m, avg ≤3h, long ≤8h, extreme, cancelled
  • sample_size < 10 → "no data, can't predict"
  • Every prediction traceable back to one row of the model

One training query — all 11 aggregates

SELECT
  origin, dest, hour_of_day, weather_bucket,
  AVG(arr_delay_minutes),
  PERCENTILE_CONT(0.5) WITHIN GROUP (…),
  COUNT(*) FILTER (WHERE arr_delay > 15)
    / COUNT(*)                -- pct_late
  …
FROM flights_enriched
WHERE EXTRACT(year FROM flight_date) IN (2022, 2023)
GROUP BY 1, 2, 3, 4
HAVING COUNT(*) >= 10;
Capstone

Predicting 2024 — one LEFT JOIN

Future flights × trained model → predictions. 20.3s on 484k flights.

The query

SELECT
  f.flight_id,
  m.median_delay AS exp_delay,
  CASE
    WHEN m.pct_late < 0.20 THEN 'low'
    WHEN m.pct_late < 0.50 THEN 'average'
    ELSE                       'high'
  END AS late_likelihood,
  ...
FROM flights_enriched fe
JOIN flights f USING (flight_id)
LEFT JOIN model_route_hour_weather m
  ON m.origin = f.origin_airport_code
 AND m.dest   = f.dest_airport_code
 AND m.hour_of_day    = fe.hour_of_day
 AND m.weather_bucket = fe.dep_weather_bucket
WHERE EXTRACT(year FROM f.flight_date) = 2024;

For a pure-SQL lookup model trained in 13 seconds, these are honest numbers. MAE grows with predicted severity because variance grows — expected behaviour.

Capstone

Resilience — failures are first-class data

Live demo: inject a corrupt row, the procedure fails & logs it, work rolls back, recovery is logged too.

1. Inject dirty data

INSERT INTO staging.weather_raw (
  airport_code, time, ...
) VALUES (
  'ATL', 'CORRUPT_TIMESTAMP', ...
);

Simulates real ETL hitting a fat-fingered upstream value.

2. CALL demo_refresh_weather_hourly();

ERROR: invalid input syntax
for type timestamp: "CORRUPT_TIMESTAMP"

HINT:  See job_log table
       for the FAILED row.

~10 ms in, the ::TIMESTAMP cast fails. The procedure catches the error and records it.

3. The audit log captures it

SELECT job_name, status, errors
FROM job_log WHERE ...

FAILED  invalid input syntax
        for type timestamp...

And weather_hourly is still 263,040 rows — work rolled back, audit persisted.

4. Fix and re-run — recovery side-by-side

DELETE FROM staging.weather_raw WHERE time = 'CORRUPT_TIMESTAMP';
CALL demo_refresh_weather_hourly();

-- job_log now shows both:
demo_refresh_weather_hourly  OK      263,040  dur=0:00:03.467
demo_refresh_weather_hourly  FAILED  NULL     dur=0:00:00.010   errors="invalid input syntax..."

Failures are recorded, not hidden. The "audited-failure" pattern keeps the audit row outside the work transaction so it survives the rollback. See REPORT §9.

Wrap — what we built, what we'd extend

What we built

  • End-to-end PostgreSQL pipeline, 3 years × 10 airports
  • Explainable prediction model — entirely in SQL
  • Per-job audit trail with first-class failure handling
  • pgTAP test suite for schemas + procedures + prediction logic

What we'd extend

  • Scale to all top-50 airports — same code, just more data
  • Add carrier as a 5th grouping key for finer predictions
  • Compare against a non-SQL baseline (linear regression, kNN)
  • Per-route per-month seasonality bucket
  • Real-time forecast feed instead of replaying 2024
