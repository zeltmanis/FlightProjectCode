Capstone

Why jobs? — raw text in, typed columns out

The CSV loads as 14 TEXT columns. A job strips, validates, and types every one.

The problem — everything is a string

-- staging.flights_raw : every column is TEXT
flight_date        '2022-01-06'   -- a date, as text
crs_dep_time       '520'          -- HHMM, as text
dep_time           '512.0'        -- a time... as a float string
cancelled          '0.0'          -- a boolean... as '0.0'
cancellation_code  ''             -- empty string, not NULL
arr_delay_minutes  '0.0'          -- a number, as text
  • No validation — a malformed value would load without error
  • Text won't sort or do math; indexes are meaningless
  • Empty string ≠ NULL; no FKs, no CHECKs possible

The fix — the job types & validates it

-- public.flights : typed, constrained
flight_date         DATE
origin_airport_code CHAR(3)      FK → airports
scheduled_departure TIMESTAMPTZ  -- HHMM → real timestamp
cancelled           BOOLEAN
cancellation_code   CHAR(1)      CHECK (A/B/C/D)
arr_delay_minutes   NUMERIC
arr_del15           BOOLEAN       -- derived
  • The database enforces validity on every write
  • Real dates/numbers → correct sorting, math, and indexes
  • FKs + CHECKs reject bad rows; NULL means "unknown"
Capstone

Batch jobs — the pipeline runs itself

Each step is a self-logging stored procedure. One call runs all nine.

Anatomy of a batch job — refresh_flights_enriched()

Every job follows the same five steps: log “started” → do the work → log “OK” — or, if anything breaks, log “FAILED” and roll it all back. 

CREATE OR REPLACE PROCEDURE refresh_flights_enriched()
LANGUAGE plpgsql AS $$
DECLARE v_job_id BIGINT; v_rows INTEGER;
BEGIN
  -- (1) record the run as RUNNING
  INSERT INTO job_log (job_name, status)
    VALUES ('refresh_flights_enriched', 'RUNNING')
    RETURNING job_id INTO v_job_id;

  TRUNCATE flights_enriched;          -- (2) idempotent rebuild

  INSERT INTO flights_enriched (...)   -- (3) the work: two joins
  SELECT f.flight_id, w_dep.temperature_c, w_dep.precipitation_mm, …
  FROM flights f
  LEFT JOIN weather_hourly w_dep
    ON w_dep.airport_code  = f.origin_airport_code
   AND w_dep.obs_timestamp = DATE_TRUNC('hour', f.scheduled_departure)
  LEFT JOIN weather_hourly w_arr
    ON w_arr.airport_code  = f.dest_airport_code
   AND w_arr.obs_timestamp = DATE_TRUNC('hour', f.scheduled_arrival);

  GET DIAGNOSTICS v_rows = ROW_COUNT;
  UPDATE job_log SET status='OK', rows_processed=v_rows … -- (4) OK

EXCEPTION WHEN OTHERS THEN              -- (5) log FAILED, rollback
  UPDATE job_log SET status='FAILED', errors=SQLERRM …;
  RAISE;
END; $$;

Why batch jobs?

  • Repeatable — rebuild the whole DB from raw with one command
  • Auditable — every run logs its row count, duration, and any error
  • Ordered — dependencies run in the correct sequence
  • Safe — a failure rolls back its work but keeps the audit row

Resilience — failures are first-class data

Live demo: inject a corrupt row, the procedure fails & logs it, work rolls back, recovery is logged too.

1. Inject dirty data

INSERT INTO staging.weather_raw (
  airport_code, time, ...
) VALUES (
  'ATL', 'CORRUPT_TIMESTAMP', ...
);

Simulates a malformed value arriving from an upstream source.

2. CALL demo_refresh_weather_hourly();

ERROR: invalid input syntax
for type timestamp: "CORRUPT_TIMESTAMP"

HINT:  See job_log table
       for the FAILED row.

~10 ms in, the ::TIMESTAMP cast fails. The procedure catches the error and records it.

3. The audit log captures it

SELECT job_name, status, errors
FROM job_log WHERE ...

FAILED  invalid input syntax
        for type timestamp...

And weather_hourly is still 263,040 rows — work rolled back, audit persisted.

4. Fix and re-run — recovery side-by-side

DELETE FROM staging.weather_raw WHERE time = 'CORRUPT_TIMESTAMP';
CALL demo_refresh_weather_hourly();

-- job_log now shows both:
demo_refresh_weather_hourly  OK      263,040  dur=0:00:03.467
demo_refresh_weather_hourly  FAILED  NULL     dur=0:00:00.010   errors="invalid input syntax..."

Failures are recorded, not hidden. The "audited-failure" pattern keeps the audit row outside the work transaction so it survives the rollback. See REPORT §9.

Architecture — ELT, four layers

Python fetches and loads. PostgreSQL does everything else.
[ Python ]                          [ PostgreSQL — Uganda DB ]

  fetch_*.py     COPY ►  staging.flights_raw      ┐  raw, all TEXT
                                  staging.weather_raw      │
                                  staging.airports_raw     ┘
                                          │
                                          │  refresh_*()
                                          ▼
                            airports / airlines / weather_hourly / flights
                                          │
                                          │  refresh_flights_enriched()
                                          ▼
                            flights_enriched     ← weather + features per flight
                                          │
                                          │  refresh_model_route_hour_weather()
                                          ▼
                            model_route_hour_weather    ← THE MODEL
                                          │
                                          │  predict_flights()
                                          ▼
                            predictions   ───▶   validate_predictions()  ───▶  validation_results

Python only loads the raw data; the database performs all cleaning and transformation — in SQL, which is version-controlled, re-runnable, and easy to inspect in DataGrip. (That's the “L before T” — load first, transform inside the DB.)

The schema — ten tables, four roles

Dimensions, facts, model, output — plus a system log. Nine foreign keys tie it together.

Dimensions reference

  • airports — code, name, lat/lon
  • airlines — carrier codes
  • routes — 90 valid pairs (derived)

Small, stable, shared by everything.

Facts events

  • flights — 1.4M, FK → airports×2, airlines
  • weather_hourly — 263k, by airport × hour
  • flights_enriched — 1:1 with flights + weather

Model & output results

  • model_route_hour_weather — 3,888 rules
  • predictions — 484k, FK → flights
  • validation_results — accuracy metrics

Why this design?

  • Star-ish / dimensional — small dimensions, one big fact; the model is a natural roll-up of that fact
  • FKs enforce integrity — a flight can't reference an airport or airline code that doesn't exist
  • Normalise dimensions, denormalise the hot path — flights_enriched pre-joins weather so the model query stays fast

Plus one system table

  • job_log — every batch run; standalone (no FK) so an audit row survives a rollback

Enrichment — joining weather to flights

For each flight, attach the weather at its airport at that hour — twice: takeoff and landing.

The two joins

FROM flights f
LEFT JOIN weather_hourly w_dep
  ON w_dep.airport_code = f.origin_airport_code
 AND w_dep.obs_timestamp =
     DATE_TRUNC('hour', f.scheduled_departure)
LEFT JOIN weather_hourly w_arr
  ON w_arr.airport_code = f.dest_airport_code
 AND w_arr.obs_timestamp =
     DATE_TRUNC('hour', f.scheduled_arrival)

LEFT JOIN so flights without a weather match still land in flights_enriched with NULL weather columns.

Capstone

The model is a table

A lookup table of historical aggregates — one row per route, hour and weather bucket.

Historical aggregates, grouped into buckets

Take every past flight (2022–2023) and sort it into buckets by route + hour + weather. For each bucket, we compute its historical delay statistics. To predict a new flight, we look up its bucket.

One row per bucket — 3,888 rows

routehourweather % latetypical delayflights seen
LAX→LAS06:00clear 3%~0 min635
MCO→DEN19:00light rain 64%~32 min89

A clear early-morning flight is almost never late; a rainy evening one often is. Buckets with fewer than 10 past flights → "not enough history, can't predict."

Built with one GROUP BY

SELECT route, hour, weather,
       AVG(delay)   AS typical_delay,
       pct_late, COUNT(*) AS flights_seen
FROM   flights_enriched
WHERE  year IN (2022, 2023)   -- learn from the past
GROUP BY route, hour, weather
HAVING COUNT(*) >= 10;        -- skip thin buckets

No Python, no ML library. One query builds all 3,888 rules — and every prediction traces back to exactly one row.

Capstone

Predicting 2024 — one LEFT JOIN

Match each 2024 flight to its route+hour+weather bucket, and return its prediction. 20s on 484k flights.

The query

SELECT
  f.flight_id,
  m.median_delay AS exp_delay,
  CASE
    WHEN m.pct_late < 0.20 THEN 'low'
    WHEN m.pct_late < 0.50 THEN 'average'
    ELSE                       'high'
  END AS late_likelihood,
  ...
FROM flights_enriched fe
JOIN flights f USING (flight_id)
LEFT JOIN model_route_hour_weather m
  ON m.origin = f.origin_airport_code
 AND m.dest   = f.dest_airport_code
 AND m.hour_of_day    = fe.hour_of_day
 AND m.weather_bucket = fe.dep_weather_bucket
WHERE EXTRACT(year FROM f.flight_date) = 2024;
